Part I · Choosing an approach

How to use this guide

6 min read

By the end of this guide you will be able to take a research question, pick a machine learning approach that fits your data, evaluate it the way a careful reviewer would, and write it up as a study someone else could check and repeat. This is the last of four guides in the Vector Research machine learning track. Python for Machine Learning taught you the tools. Machine Learning Foundations taught you the models and the basic workflow. Deep Learning in Practice taught you to build and train neural networks in PyTorch. This guide is about judgment: which method, which evaluation, which comparison, and which claim your evidence can support.

What you'll be able to do when you finish

  • Frame a question as a machine learning task and decide what kind of contribution your project makes.
  • Choose a strong approach for tabular data, time series, text, high-dimensional scientific data, survival times, satellite images, simulations, molecules and proteins, images, and small or partly labeled datasets.
  • Design an evaluation that matches how your model would really be used, with nested cross-validation, grouped or time-ordered splits, and external validation where possible.
  • Find and remove data leakage using a published checklist.
  • Compare models with the right statistical test, and say honestly when a difference is just noise.
  • Tune hyperparameters efficiently and report the search.
  • Measure calibration and wrap any model's predictions in intervals with a coverage guarantee (conformal prediction).
  • Explain what a model learned, check it for fairness across groups, and know when an explanation is or isn't evidence.
  • Tell prediction questions from causal questions, and estimate a treatment effect from observational data with its limits stated.
  • Read, reproduce, and extend a published ML paper, and report your own study with the checklists reviewers use.

What you need first

You should be comfortable with everything in Machine Learning Foundations: pipelines, cross-validation, the standard metrics, the classic models, tree ensembles, and the basics of tuning. When this guide builds on one of its chapters, it says so ("Machine Learning Foundations, Chapter 5"). You'll also want Deep Learning in Practice if your data is images, audio, or long text, because this guide sends you there for all PyTorch code, CNNs, transformers, fine-tuning, and training recipes. For general statistics (confidence intervals, t-tests, effect sizes, multiple comparisons), the companion guide is Statistics for Research.

How each chapter is built

Each chapter opens with what it covers and why it matters for a research project. Then come the ideas in plain words, the key formula where there is one, code you can run, and the mistakes that most often sink student projects. Every printed result in this guide came from actually running the code. Each chapter ends with a short Check yourself list. If you can answer those without looking back, move on.

Running the code

Use Google Colab. It's free, runs in your browser, and comes with scikit-learn, NumPy, pandas, and matplotlib already installed. Code blocks within a chapter build on each other, so run them in order in one notebook. Most examples use only scikit-learn and NumPy, and their printed output is shown underneath. A few examples use extra libraries (XGBoost, LightGBM, CatBoost, Optuna, SHAP, sentence-transformers, Captum, Fairlearn, Gymnasium). Those blocks have no output shown, and each one says how to install what it needs with !pip install. This guide was checked against scikit-learn 1.9.1. Check your version with import sklearn; print(sklearn.__version__). If a number differs from the printed output in the last decimal place, a library version is the likely reason. Timings depend on your computer.

How to use the playbooks

Chapter 17 has step-by-step recipes for the most common student project types: tabular prediction, image classification, text classification, time-series forecasting, biomarker discovery from high-dimensional data, and unsupervised subtype discovery. A table at the end of that chapter covers many more types, including survival analysis, audio, object detection, NER, RAG, recommenders, molecules, proteins, satellite imagery, simulation surrogates, multimodal models, and deployment. If you already have a project, read Chapter 1, find your playbook or table row in Chapter 17, and follow its links back to the chapters it needs. Then read the rest when you have time.

What counts as an ML research contribution

6 min read

Training a model is not the same as doing research. This chapter shows the kinds of contributions a machine learning project can make, how to turn a question into a well-defined ML task, and how to match your data and question to an approach.

Five kinds of contribution

A research project has to add something that wasn't known or available before. In machine learning, that addition usually takes one of five forms.

Contribution What's new Student-sized example What reviewers will check
New application or question Using ML to answer a question in another field Predicting which lakes will have harmful algal blooms from public water-quality data Is the question important, and does the evaluation match real use?
New dataset Data that didn't exist, collected and labeled carefully 2,000 labeled photos of a local invasive plant, with an annotation guide and agreement statistics Labeling quality, documentation, licensing, and a baseline result
New method A change to how models are built or trained A new feature-engineering step for sensor data, tested across several datasets Fair comparison with strong baselines, ablations, and statistics
Evaluation or benchmark study A careful test of existing methods Do skin-lesion classifiers perform equally well across skin tones? Rigor of the test design, not the novelty of the model
Replication Checking whether a published result holds Re-running a paper's code on new data and finding the reported accuracy was inflated by leakage Faithful reproduction, clear documentation of differences

Most strong student projects are new applications, new datasets, or evaluation studies. New methods are the hardest to do convincingly, because you must show the method beats well-tuned alternatives on more than one dataset. Replications are underrated. A clean replication that finds a flaw is a real contribution, and Kapoor and Narayanan (2023) built an influential paper around exactly that kind of work (Chapter 7).

Framing a question as an ML task

A research question becomes a machine learning task when you can name five things precisely. "Can we predict diabetes?" isn't framed yet. This is:

Element Question to answer Example
Unit of analysis One row is one what? One adult patient at a routine checkup
Inputs What is known at the moment of prediction? Age, BMI, blood pressure, and fasting glucose from that visit
Output What exactly are you predicting, and how was it measured? A diabetes diagnosis within 5 years, from medical records
Population Who should the model work for? Adults aged 30 to 70 at primary care clinics
Use What decision would the prediction support? Flagging patients for an earlier glucose tolerance test

The use row decides your evaluation. If the model will flag patients for a follow-up test, missing a sick patient is worse than an extra test, so recall at a fixed false-positive rate matters more than accuracy. If the model will be used at a different clinic, you need an external test set (Chapter 7). If it will be used next year, you need a time-based split (Chapter 3). Writing this table before you touch the data prevents most evaluation mistakes.

Some questions aren't prediction questions at all. "Does this supplement lower blood pressure?" is a causal question, and a model that predicts blood pressure well can still give the wrong answer to it (Chapter 13). "Are there subtypes of this disease?" is a discovery question, and its evidence looks different from a test-set score (Chapter 14).

The baseline habit

Every result in a research project needs a reference point. Use at least two baselines:

  1. A trivial baseline that uses no real information: predicting the most common class, the training mean, or yesterday's value. It tells you whether the problem is even hard.
  2. A simple strong baseline: logistic or linear regression on sensible features, a TF-IDF classifier for text, or a seasonal-naive forecast for time series. It tells you whether your fancy model is worth its complexity.

If you can, add a third: the published or current-practice baseline, such as the best result reported on the same dataset, or the rule doctors use today. "Our model reached an AUC of 0.91" means nothing alone. "Our model reached 0.91, compared with 0.88 for logistic regression and 0.84 for the clinical risk score in current use" is a finding.

Scope your project to what you can evaluate

The best student projects are narrow enough to evaluate thoroughly. "AI for cancer" can't be evaluated. "Do classifiers trained on one public chest X-ray dataset keep their accuracy on a second dataset from a different hospital?" can be evaluated in a summer with free data and Colab. When you choose between two ideas, pick the one where you can describe the test set in one sentence.

Check yourselfAnswer out loud or on paper before moving on.
  1. Name the five kinds of ML research contribution, and give one student-sized example of an evaluation study.
  2. Write the five-row framing table (unit, inputs, output, population, use) for a model that predicts whether a student will drop a class.
  3. Why does the "use" of a model decide how you should evaluate it? Give an example.
  4. What two baselines should every project include, and what does each one tell you?
